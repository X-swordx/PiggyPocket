# 需求规格（Specs）

这里存放**进入开发前**的需求 spec。它是 AI 和人都要遵守的「做完了」的定义。

## 什么时候写

| 改动 | 用哪个模板 | 是否必须用户确认 |
| --- | --- | --- |
| 新页面、新组件、接口契约变更、跨端链路 | `templates/spec.md` | 是 |
| 小功能，能用现有组件/接口拼出来 | `templates/feature-card.md` | 是（理解卡） |
| Bug 修复 | `templates/bugfix.md` | 复现契约确认后再修 |

小功能如果发现要新增页面/组件、改表结构、改接口契约，立即升级为完整 spec。

## 文件命名

```
docs/specs/YYYY-MM-DD-<需求名>.md
```

例如：`docs/specs/2026-10-25-recipe-inspiration.md`。

## 三条硬规则

1. **每条 US 至少被一条 AC 覆盖。**
2. **每条 AC 必须写「怎么验」**，并说清是哪种测试：
   - 纯函数测试
   - 组件测试
   - 后台测试（服务层/路由/契约）
   - 真实页面 BOT-n
   - 人工走查（只能用于视觉/真机兼容性，必须写原因）
3. **需要真实全栈才能判定的 AC 必须有 BOT 用例**：对接层、缓存失效、真实持久化、跨端接线、整屏交互。

## BOT 用例格式

BOT = 用 chrome-devtools / `miniprogram-automator` 在真实页面上照着操作。每条都要能独立执行：

```markdown
- **BOT-1** 〔验证 AC-2, AC-3〕
  - 前置：stage 环境，已登录用户，视口 375x812
  - 步骤：1. 打开… 2. 输入… 3. 点击…
  - 预期：看到…；接口返回 200；无 console error
  - 截图：第 3 步后截一张
```

指针交互必须用 `document.elementFromPoint(x, y)` 选目标，不能手选元素，否则会测到真实鼠标到不了的路径（假绿）。

## UI/UX 验收

走了设计阶段的需求，在 AC 里追加 `AC-UI-n`：

- 信息结构、层级、关键文案
- 亮色/暗色
- 窄屏（320/375）和宽屏，无横向滚动
- 键盘可操作、状态不只靠颜色表达
- 加载/空/错误/禁用态
- 设计 token（颜色/字号/间距/圆角）没有硬编码

## 完成定义（DoD）

- [ ] 所有 AC 都有「怎么验」，并实际通过
- [ ] BOT/人工走查有截图或记录
- [ ] 代码规范、type-check、单测/集成测试通过
- [ ] 已部署到 stage，并完成 stage 人工验收
- [ ] production 只合并了本次已验收的 `feature/<task>`
- [ ] 发布后有健康检查、日志/错误率观察窗口
- [ ] 有可回滚的 tag 和 release manifest
