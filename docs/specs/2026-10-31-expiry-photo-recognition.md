# 到期管家：拍照识别商品信息

## 问题陈述

用户往到期管家里添加物品时，要手工抄写「物品名称、生产日期、保质期」三项。包装上的名称字号小，生产日期和保质期往往是点阵喷码，印在瓶底、袋口、侧面，光线差或曲面反光时很难看清；而且商品名称和日期喷码通常不在同一面，一张正面照往往只能拿到名称。一次买多件同类商品时要重复录入，容易抄错日期。

用户原本期望「扫一下二维码就能带出这三个字段」，但普通商品条码（EAN-13）里只有厂商和商品编码，不含生产日期；日期是另外喷印的文字。少数符合 GS1 标准的二维码才会把生产日期、到期日编进码里，国内覆盖率还很低。因此单靠「扫码」解决不了日期问题。

## 解决方案

在「添加物品」页增加一个「拍照识别」按钮：

1. 用户点一次「拍照识别」，先拍**商品名称面**；上传成功后询问是否继续拍**日期喷码面**，第二张可以跳过。两张都从相机或相册选。
2. 最多两张照片上传到现有 OSS，后端一次把 1～2 张图按 [名称面, 日期面] 的顺序交给视觉理解模型，综合读出名称、生产日期、保质期/到期日。
3. 后端把结果归一化、校验、补齐（例如只印了到期日时反推生产日期），返回结构化字段。
4. 小程序把结果**预填到现有表单**，名称面照片作为物品图片；用户核对、修改后点「确认添加」才真正入库。

不新增表结构，不新增页面，不改现有新增/编辑接口。识别只是「帮用户填表」，不是「替用户保存」。

## 用户故事

- **US-1** 作为到期管家用户，我想要拍一张包装照片就自动填好名称、生产日期和保质期，以便不用逐项手抄。
- **US-2** 作为到期管家用户，我想要在保存前看到并修改识别结果，以便日期识别错了不会悄悄入库。
- **US-3** 作为到期管家用户，我想要识别失败或服务不可用时仍能继续手动填写，以便录入流程不被打断。
- **US-4** 作为到期管家用户，我想要识别用的那张照片同时作为物品图片，以便不用再拍一次。
- **US-5** 作为到期管家用户，我想要在包装只印了到期日、或只印了生产日期和到期日时也能自动补出另一个字段，以便少填一项。
- **US-6** 作为到期管家用户，我想要在识别结果不完整时被告知还缺什么，以便知道下一步该补哪一项。
- **US-7** 作为开发者，我想要识别接口只读不写、不接受 `userId`，并且只允许抓取本站 OSS 图片，以便不扩大现有小程序裸接口的风险。
- **US-8** 作为运维者，我想要视觉模型未配置或调用失败时只让识别功能降级，不影响应用启动和其他功能，以便配置问题不会扩大成线上故障。
- **US-9** 作为到期管家用户，我想要分两次拍商品名称面和日期喷码面，以便两面信息都能被识别，而不是只能识别正面。

## 验收标准

### 入口与预填

- **AC-1** 「添加物品」页显示「拍照识别」按钮；点击后先调起相机/相册选**名称面**，上传成功后弹窗询问是否继续拍**日期面**，用户可确认继续、也可跳过；两次选图都只选 1 张并使用压缩图。〔覆盖 US-1, US-9〕
  - **怎么验**：真实页面 BOT-1 检查按钮可见、选图入口和「是否继续拍日期面」弹窗；微信小程序真机人工走查检查相机权限、第二张跳过与取消行为。

- **AC-2** 名称面和日期面都上传后，按 `[名称面, 日期面]` 顺序调用识别接口；识别成功时表单的 `name`、`productionDate`、`shelfLifeValue`、`shelfLifeUnit` 和 `imageUrl` 被预填，`imageUrl` 为名称面照片，且页面实时算出的到期日与后端返回的 `expiryDate` 一致。〔覆盖 US-1, US-4, US-9〕
  - **怎么验**：真实页面 BOT-1 依次选两张 fixture 图片，检查五个字段被填入、图片区显示名称面照片、到期日预览出现；后台测试检查请求按两张图传入、接口返回的 `expiryDate` 与「生产日期 + 保质期」计算结果一致。

- **AC-3** 识别结果不会自动入库；只有用户点「确认添加」后才发出 `POST /expiry-items`，且请求体中的日期/保质期字段与表单当前值一致。〔覆盖 US-2〕
  - **怎么验**：真实页面 BOT-1 在识别后不点保存，确认没有创建请求；再点保存，检查请求体与列表新增记录。

- **AC-4** 表单已有内容时，识别前弹出覆盖确认；用户取消则原有内容完全不变，用户确认才覆盖。〔覆盖 US-2〕
  - **怎么验**：真实页面 BOT-3 先手填名称和日期，再触发识别，点取消后检查字段不变；再触发一次点确认，检查被覆盖。

### 识别结果质量

- **AC-5** 识别不到任何可用字段时，接口返回 `recognized=false` 和面向用户的中文 `warnings`，小程序不覆盖表单已有内容，并提示「未识别到…请手动填写」。〔覆盖 US-3, US-6〕
  - **怎么验**：纯函数测试覆盖空结果/无字段结果；真实页面 BOT-2 用一张不含标签的图片，检查表单保持不变且出现提示。

- **AC-6** 日期和保质期按以下规则归一化，缺失字段能补则补，补出来的字段带明确 `warnings`：〔覆盖 US-5, US-6〕
  - 接受 `YYYY-MM-DD`、`YYYY/MM/DD`、`YYYYMMDD`、`YYYY年M月D日`，统一输出 `YYYY-MM-DD`；
  - 同时有生产日期、到期日和保质期时，以印刷的生产日期和到期日为准；二者算出的保质期与印刷值相差超过 3 天时，按日期反推保质期并告警；
  - 只有生产日期和到期日时，按整月差反推 `month`，不是整月则按天数差反推 `day`；
  - 只有到期日和保质期时，反推生产日期并告警「生产日期由到期日和保质期推算」；
  - 只有生产日期时，保留生产日期，告警缺保质期；只有到期日时，不猜生产日期，告警缺生产日期。
  - **怎么验**：纯函数测试逐条覆盖上述分支和边界（1 月 31 日加 1 个月、闰年 2 月 29 日、整月差与天数差切换）；后台测试确认接口响应中的 `warnings` 原样透出。

- **AC-7** 非法或自相矛盾的日期被拒绝或降级，不会进入表单：生产日期晚于今天、到期日早于生产日期、保质期 `<1`、天数 `>3650`、月数 `>120`、无效日历日期（如 `2026-02-30`）。〔覆盖 US-2, US-6〕
  - **怎么验**：纯函数测试覆盖每类非法输入，断言对应字段为 `null` 且 `warnings` 非空；后台测试确认不会把非法值返回给前端。

- **AC-8** 接口返回结构固定：`recognized`、`name`、`productionDate`、`shelfLifeValue`、`shelfLifeUnit`、`expiryDate`、`confidence`、`warnings`；字段缺失时为 `null`，不省略键。〔覆盖 US-6〕
  - **怎么验**：后台测试对成功、部分识别、完全未识别三种响应做契约断言。

### 失败与降级

- **AC-9** 视觉模型未配置时接口返回 503；上游超时（20 秒）或报错返回 502；图片地址不合法返回 400。小程序收到非 2xx 时提示失败原因，并保持表单可编辑。〔覆盖 US-3, US-8〕
  - **怎么验**：后台测试注入返回 `null` 的模型、抛超时/异常的假模型、非法 `imageUrl`，断言 503/502/400；真实页面 BOT-2 检查失败提示与表单可用性。

- **AC-10** 识别接口不写库、不接受 `userId`；`imageUrls` 里每个 host 必须与配置的 OSS host 一致；任一非 `image/*` 内容、单张超过 8MB、或两张合计超过 12MB 返回 400。〔覆盖 US-7〕
  - **怎么验**：后台测试用外部域名、`file://`、非图片 Content-Type、超大单图、两张合计超限分别断言 400；检查接口实现中没有注入 repository、没有创建/更新操作。

- **AC-13** 识别请求体为 `{ imageUrls: string[] }`，长度 1～2；空数组或超过 2 张返回 400。只传 1 张时按原单图逻辑识别；传 2 张时两张都下载并按传入顺序一起交给模型。〔覆盖 US-9〕
  - **怎么验**：后台测试分别用 1 张、2 张、0 张、3 张调用，断言下载次数、模型收到的图片数量和顺序、以及 400 响应；路由契约测试断言 DTO 校验生效。

- **AC-11** 缺少 `VISION_MODEL_NAME` 时应用正常启动，只有识别接口返回 503；菜谱生成、语义搜索、到期管家增删改查不受影响。〔覆盖 US-8〕
  - **怎么验**：后台测试构造空配置的模块工厂，断言返回 `null` 且应用可创建；Stage 环境把该变量留空启动一次，检查 `/api/health/ready` 和到期管家列表。

- **AC-12** 不新增表字段、不新增 migration，`expiry_items` 实体和现有新增/编辑接口契约不变。〔覆盖 US-4, US-7〕
  - **怎么验**：人工走查 migration 目录无新增、实体无改动；后台 `npm run build` 和 `npm test` 通过。

## 测试决策

### 接缝

本次新增两个后端接缝，前端不新增测试框架（`mobile` 目前没有 test 脚本和测试依赖）：

1. **纯函数接缝（最高优先）**：`normalizeRecognition(raw)` 负责日期格式归一、字段补齐、合法性校验、告警生成。只依赖输入输出，不起服务、不连模型。覆盖 AC-5、AC-6、AC-7。
2. **服务层接缝**：识别 service 注入视觉模型（接口形状只需 `invoke(messages)`），测试用假模型返回固定 JSON、抛超时、抛异常、返回非法 JSON，并断言 1～2 张图的下载与消息组装。覆盖 AC-8、AC-9、AC-10、AC-11、AC-13。
3. **路由契约**：controller 只做参数校验和异常映射，用 mock service 断言 200/400/502/503 与响应键。覆盖 AC-8、AC-9。
4. **真实页面 BOT**：uni-app H5 构建用 chrome-devtools 驱动，覆盖 AC-1～AC-5 和 AC-UI-1。微信小程序相机/相册是原生能力，`miniprogram-automator` 无法操作，真机部分只能人工走查，原因写在对应 AC 里。

现有先例：`nest-service/src/modules/expiry/expiry-search-ranking.spec.ts` 是纯函数测试风格；`docs/specs/README.md` 规定 BOT 用 `chrome-devtools` / `miniprogram-automator`。好测试只断言外部行为：给定模型输出得到什么结构化结果、给定异常得到什么状态码，不断言 prompt 文案。

### 主流程回归

会影响「添加物品」页，因此 Stage 验收必须回归：

- 不点识别、纯手填新增物品 → 保存成功，字段和到期日与改动前一致；
- 编辑已有物品 → 打开时字段回填正确，保存后到期日按生产日期 + 保质期重算；
- 原有「点击上传物品图片」仍可单独使用，识别按钮不抢它的点击区域；
- 到期管家列表、即将到期/已过期筛选、搜索不受影响。

## 实现决策

### 接口契约

新增 `POST /api/expiry-items/recognize`，请求体 `{ imageUrls: string[] }`，长度 1～2，按 `[名称面, 日期面]` 顺序；无 `userId`，不写库。识别接口尚未在 production 发布，本次直接替换旧的 `{ imageUrl }` 契约，不保留兼容字段。

成功 200：

```json
{
  "recognized": true,
  "name": "伊利纯牛奶",
  "productionDate": "2026-10-01",
  "shelfLifeValue": 6,
  "shelfLifeUnit": "month",
  "expiryDate": "2027-04-01",
  "confidence": "high",
  "warnings": []
}
```

- 缺失字段统一返回 `null`，键不省略；`confidence` 为 `high | medium | low`，模型没给或值非法时按 `low`。
- `recognized` 为「至少有一个可用于填表的字段」；只有名称也算 `true`，但 `warnings` 说明缺日期。
- `expiryDate` 只用于前端预览；保存时仍由服务端按生产日期 + 保质期重算，前端不提交 `expiryDate`。
- 状态码：400 参数/图片不合法；502 上游超时或失败；503 视觉模型未配置；200 只要模型有响应（包括没识别出东西）。

### 视觉模型

- 新增独立配置 `VISION_MODEL_NAME`，不要复用文本模型 `MODEL_NAME`；复用现有 `OPENAI_API_KEY` / `OPENAI_BASE_URL`，已验证同端点支持视觉模型，不新增独立 key。
- 模型实例：温度 0，`maxRetries: 0`，超时 20 秒，`thinking: { type: "disabled" }`；提示词说明「可能有一到两张同一商品不同面的照片，第 1 张是名称面、第 2 张是日期面」，要求综合所有图片、只输出 JSON、不确定就返回 null、不要猜；解析时容忍 markdown 代码块，不依赖 `response_format`。
- 视觉模型缺失时工厂返回 `null`，识别接口抛 503，应用照常启动；与现有 AI 模块的降级方式保持一致。
- `.env.example` 和 Stage env 模板只加占位符，不写真实 key；部署 compose 透传 `VISION_MODEL_NAME`。

### 图片处理与安全

- 小程序复用现有 `uni.chooseMedia`（`count:1`、`mediaType:['image']`、`sizeType:['compressed']`）和 `uploadToOSS(tempFilePath, 'items')`；名称面上传成功后弹窗询问是否继续拍日期面，第二张可跳过；识别成功后把名称面照片填进表单 `imageUrl`，日期面照片不单独保存。
- 后端用 `fetch` 并行下载 1～2 张图片，逐张校验：URL 为 http/https、host 等于配置的 OSS host、响应 `Content-Type` 以 `image/` 开头、单张读取上限 8MB；两张合计不超过 12MB。通过后都转成 base64 data URL 传给模型。这样不依赖模型侧能否访问私有签名 URL，也避免任意 URL 抓取（SSRF）。
- 不引入图片处理库，不做服务端裁剪/压缩；依赖客户端 `compressed`。

### 归一化规则

- 纯函数负责：日期格式归一、字段补齐、合法性校验、冲突处理、告警文本。
- 月份加减复用现有「到期日 = 生产日期 + 保质期」的 UTC 算法，保证和保存时的计算一致。
- 保质期取值：`day` 1～3650，`month` 1～120；超出范围一律置 `null` 并告警，不截断。
- 生产日期不得晚于服务器当天（东八区）；到期日必须晚于生产日期。
- 印刷值优先级：生产日期/到期日 > 保质期；冲突超过 3 天时按日期反推保质期，并告警。
- 只印到期日、没有生产日期时，只有同时拿到保质期才反推生产日期；反推结果必须通过上述合法性校验，否则留空。

### 小程序交互

- 识别按钮放在图片上传区下方，文案「拍照识别」，带相机图标；提示文案说明可拍名称面和日期面、日期面可跳过。上传/识别中显示 loading 且禁用重复点击。
- 点击后依次引导：选名称面 → 上传 → 弹窗「是否继续拍日期面」；确认则继续选日期面并上传，跳过则只带名称面识别。
- 识别完成后只在表单**为空**时直接填入；任一目标字段已有内容时，先弹「识别结果将覆盖已填写的内容」确认框，取消则不写任何字段。
- 识别成功后在表单顶部显示「AI 识别结果，请核对后保存」；有点击可关闭的 `warnings` 列表。
- 识别失败（网络、502、503）只做 toast/顶部提示，不清空表单，不阻塞手动输入。
- 编辑已有物品时也显示识别按钮，行为同上（覆盖前确认）。

### 环境与部署

- 后端 `.env` 新增 `VISION_MODEL_NAME`（复用现有 `OPENAI_API_KEY` / `OPENAI_BASE_URL`）。
- `deploy/cloud/.env.example`、`deploy/stage/.env.stage.example` 只加占位符；`deploy/cloud/docker-compose.yml` 增加 `VISION_MODEL_NAME` 透传。
- 这是纯增量接口，无 migration；上线时只需重建 api 容器（改了 `.env` 必须重建才生效）。

## 涉及层与路径

- **路径**：B（新增后端识别能力）+ C（改老页面旁路，不新建页面）。
- **涉及层**：小程序页面与 service、后端 controller / dto / service / 纯函数 / 模块工厂、部署 env 与 compose。
- **设计产物**：不需要新线框图；沿用现有添加物品表单，识别流程改为两次引导选图并复用现有提示区，`DESIGN.md` 不动。

## 不在范围内

- 条码/二维码反查商品库（聚合数据、阿里云云市场、GS1 官方登记接口）。
- GS1 Digital Link / AI 11 / AI 17 的码内日期解析。
- 新增条码字段、商品库匹配、品牌/规格/厂家字段。
- 超过两张照片、相册多选、批量识别、连续扫码入库。
- 识别历史、用户纠错反馈、按商品记忆保质期。
- 自动保存或后台批量识别。
- 药品、美妆、日用品标签的专用模型调优（同一模型可用，但不单独验收精度）。
- 服务端图片压缩、旋转校正、透视矫正。

## 补充说明

### 2026-11-01 修订：支持两张照片

首版只支持一张照片，stage 真机验收时发现商品名称与生产日期通常不在同一面，单张正面照拿不到日期。本次改为「点一次识别，依次引导拍名称面、日期面，第二张可跳过」，接口改为 `{ imageUrls: string[] }`（1～2 张），名称面照片作为物品图片。接口尚未在 production 发布，直接替换契约、不保留旧字段。

### 调研结论

- **没有**「扫二维码直接返回生产日期 + 到期日期 + 商品名」的通用 API。普通 EAN-13 条码只含 GTIN；日期是另外喷印的文字。GS1 标准二维码可以带 AI 11（生产日期）、AI 17（到期日）、AI 15（保质期），但国内覆盖率低，官方平台（[国家二维码综合服务平台](https://dl.gs1cn.org/digital-link/home.html)、[中国食品（产品）安全追溯平台](https://www.chinatrace.org/platform/introduction)）也没有公开 API。
- 商品名反查有现成商业接口：聚合数据、阿里云云市场、[极数本源 GS1](https://apizero.cn/marketplace/barcode-gs1)，约 0.01–0.03 元/次，但覆盖率不保证。本次不接。
- 日期识别没有食品标签专用 API；行业做法是通用 OCR + 规则，或直接上视觉大模型。重庆市场监管局的「预包装食品标签 AI 巡检」就是 OCR + 大模型（[来源](https://www.cq.gov.cn/ywdt/jrcq/202507/t20250717_14822158_app.html)）。
- 自动保存的错误率不可接受（公开项目约 14%），加确认环节后可降到 2% 以下，因此本方案强制「预填 + 人工确认」。

### 前置验证（已完成）

现有 `OPENAI_BASE_URL` 是方舟 Agent Plan 端点 `https://ark.cn-beijing.volces.com/api/plan/v3`。已用现有 key 验证：

- 多数视觉模型返回 `UnsupportedModel`，`doubao-seed-2.0-mini` 可用，因此 `VISION_MODEL_NAME=doubao-seed-2.0-mini`，不需要独立端点或 key。
- 开启深度思考时单图约 4.9 秒；`thinking: { type: "disabled" }` 后约 1.6–2.2 秒，满足同步交互要求。
- 用生成的包装图（标准喷码、旋转 + 点分日期、无标签照片三种）跑完整 service 链路，字段与归一化结果符合预期，分别约 1.6s / 2.2s / 2.0s。

### 风险

- **识别精度**：点阵喷码、曲面、反光、低对比度会掉点；`confidence` 是模型自报，未校准，只能作为提示，不能作为自动保存依据。所有结果都必须人工确认。
- **两图覆盖有限**：引导用户拍名称面和日期面后，仍可能两张都拍同一面或漏拍日期；模型可能缺字段，结果必须人工确认。
- **成本**：视觉模型按 token 计费，一张压缩图约 0.002–0.004 元（[方舟模型价格](https://www.volcengine.com/docs/82379/1544106)），识别失败和重复点击都会产生费用；按钮禁用和超时可控制浪费。
- **隐私**：照片会离开设备，上传 OSS 并发给模型供应商；现有隐私弹窗已覆盖图片上传，需在隐私协议里补充「图片用于 AI 识别」的说明（文案更新不在本 spec 的代码范围内，但上线前必须完成）。
- **图片留存**：识别用的照片同时作为物品图片长期保存在 OSS；不做单独的临时清理。

### 待定

- `confidence` 的阈值是否需要影响前端提示样式（例如 `low` 时强制展开 warnings），等 BOT 看到真实输出后再定，首版统一提示「请核对」。
